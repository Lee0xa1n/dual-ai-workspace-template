# 两个 AI 助手共用一个仓库：云端 + 本地分工协作模板

## 这篇教程能帮你做到什么

如果你同时用两个 AI 助手，一个在云端、一个在本地电脑上，很快会遇到三个麻烦：

1. **两人看不到对方的聊天记录。** 云端那个不知道本地那个干了什么，反过来也一样，任务口头交代完就丢了。
2. **分工不清。** 两个都去做同一件事，或者都没做，互相等。
3. **成果找不到。** 做完了东西放在哪、哪个版本是最新的，没人说得清。

解决办法很简单：建一个私有 GitHub 仓库，当作两个助手的共用工作台。任务写进仓库，成果也写回仓库，状态随时可查。谁该干什么、干到哪一步，都落在文件里，不靠任何一方的记忆。

这个模板以 Muse（云端）和 DeepSeek Harness（本地）这一对为具体例子。换成别的云端 + 本地组合也一样，改一下名字和分工就行。

适合谁：

- 同时用两个 AI 助手的人，一个在云端、一个在本地电脑上；
- 想让助手帮你干活，但不想每次都口头重复交代进度的人；
- 愿意花十几分钟搭一次，之后长期复用的人。

不适合谁：只用一个助手的人——一个助手不需要这个，直接在对话里交代就行。

## 准备工作

- 一个 GitHub 账号；
- 两个 AI 助手：一个云端助手，一个本地助手；
- 各自的分工先想清楚：云端助手擅长联网检索、网站与账号操作；本地助手擅长本地文件处理、本地代码运行。分工不是死规矩，任务文件里可以直接指定执行方。

## 步骤一：建一个私有仓库

在 GitHub 上新建一个仓库，可见性选 **Private（私有）**。任务和成果都在里面，只有你和两个助手能看到。

名字随你取，比如 `agent-hub`。不用勾选初始化 README，后面五样东西你自己放。

然后把仓库地址分别告诉两个助手，让它们都能读写这个仓库。

## 步骤二：放进五样东西

仓库里只需要五样东西，各干各的活：

| 东西 | 是什么 | 干什么用 |
| --- | --- | --- |
| `tasks/` | 任务区 | 一项任务对应一个文件，谁要干活先来这里领 |
| `results/` | 成果区 | 任务产出放在这里，和任务文件同名对应 |
| `shared/` | 共享资料 | 双方都能调用的背景资料和说明文档 |
| `STATUS.md` | 状态看板 | 记录接入状态和任务进展，想知道进行到哪一步就看它 |
| `PROTOCOL.md` | 协作协议 | 双方都要遵守的规则，见步骤三 |

建法：在仓库里新建这三个目录和两个文件，内容先空着也行，下面三步再往里填。

## 步骤三：写 PROTOCOL.md（协作协议）

这是整个模板的核心：两个助手都要遵守的规则。把下面七条写进去。

### 任务文件

- 位置：`tasks/`；命名：`YYYY-MM-DD-简短标题.md`。
- 内容至少包含以下字段：
  - **发起方**：用户 / 云端助手 / 本地助手
  - **目标**：以一句话说明预期结果
  - **具体要求**：步骤、约束条件与交付形式
  - **状态**：待领取 / 进行中 / 已完成 / 已阻塞
  - **进展记录**：按时间顺序追加，不修改既有记录

### 执行规则

1. 领取任务前，先将状态修改为「进行中」并注明执行方，避免双方重复执行同一任务。
2. 每次开始工作前，先同步仓库最新状态（本地执行 `git pull`，云端读取最新内容）；提交前再次同步。发生冲突时以最新提交为基础协商处理，不得强制覆盖对方成果。
3. 成果文件存放于 `results/`，与任务文件同名；任务完成后将状态修改为「已完成」，并在任务文件中注明成果路径。
4. 因信息不足或条件不具备无法继续时，将状态修改为「已阻塞」，并在进展记录中说明缺失项与所需支持。
5. 不删除对方的文件与记录；任务作废时，在文件顶部标注「已作废」及原因。
6. 禁止写入仓库的内容包括：密码、验证码、API 密钥、支付信息等敏感凭据。仓库为私有仓库，亦不例外。
7. 用户的最新指示优先于本协议。本协议如需修改，须经用户确认后执行。

### 分工参考

- 云端助手优先承担：联网检索、网站与账号操作、跨日跟进、文字整理与分析。
- 本地助手优先承担：本地文件处理、本地代码运行、Windows 软件操作及依赖本地环境的事项。
- 用户可在任务文件中直接指定执行方。

## 步骤四：写 STATUS.md（状态看板）

状态看板只干一件事：让任何人打开它，十秒内知道现在进行到哪一步。格式不用复杂：

```markdown
# 状态看板

## 接入状态
- 云端助手：已接入
- 本地助手：已接入

## 任务进展
| 任务 | 状态 | 执行方 | 成果 |
| --- | --- | --- | --- |
| 整理资料 | 待领取 | — | — |
```

任务状态变化时，执行方负责同步更新这张表。上面这份是示例格式，里面的任务名只是占位。

## 步骤五：写第一个任务文件

在 `tasks/` 里新建第一个任务文件，文件名按 `YYYY-MM-DD-简短标题.md` 的格式，日期写创建任务那天。

下面是一份填好的通用示例，**这只是示例，不是真实任务**，照着这个格式写就行：

```markdown
# 整理资料

- **发起方**：用户
- **目标**：把散落在各处的资料整理成一份清单
- **具体要求**：
  1. 收集指定范围内的资料，按主题分类；
  2. 输出一份清单，注明每份资料的来源和要点；
  3. 交付形式：写成一个 Markdown 文件，放在 results/，与本任务文件同名。
- **状态**：待领取
- **进展记录**：
  - （执行方领取后，在此按时间顺序追加，不修改已有记录）
```

要点：目标一句话写清要什么结果；具体要求写清步骤、约束和交付形式；状态一开始就是「待领取」。

## 步骤六：执行方领任务、写回成果

一个任务从发出到完成，走这四步：

1. **领任务**：执行方在 `tasks/` 里找到任务文件，先把状态改成「进行中」，注明自己是执行方，再开始干活。这一步是防重复执行的关键。
2. **开工前同步**：开始工作前先同步仓库最新状态（本地执行 `git pull`，云端读取最新内容），提交前再同步一次。有冲突时以最新提交为基础协商处理，不强制覆盖对方的成果。
3. **写回成果**：做完后把成果文件放进 `results/`，与任务文件同名；再把任务状态改成「已完成」，并在任务文件里注明成果路径。
4. **更新看板**：顺手更新 `STATUS.md` 里的任务进展。

中途卡住了怎么办：信息不足或条件不具备，无法继续时，把状态改成「已阻塞」，在进展记录里写清缺什么、需要什么支持，等发起方补齐再继续。不要闷头猜，也不要直接放弃。

## 使用规则：日常记住这几条

- **任务拆小，一次一个。** 别一次扔一堆任务给执行方，拆到自然的决策点再交接。
- **状态先改再开工。** 领任务先改状态，改完再动手，这是防重复的唯一办法。
- **成果写回仓库，不写在聊天里。** 聊天记录另一个助手看不到，仓库双方都能看到。
- **不删对方的东西。** 任务作废时在文件顶部标注「已作废」及原因，不要直接删文件。
- **敏感凭据绝不进仓库。** 密码、验证码、API 密钥、支付信息，一律不写。仓库是私有的也不行。
- **用户最新指示优先。** 你的最新指示高于协议，协议要改须经你确认。

## 今天就能开始

1. 建一个私有仓库，地址发给两个助手。
2. 放进 `tasks/`、`results/`、`shared/`、`STATUS.md`、`PROTOCOL.md` 这五样。
3. 把步骤三的七条规则写进 `PROTOCOL.md`。
4. 在 `tasks/` 里写第一个任务文件，照着步骤五的示例格式填。
5. 让执行方去领，成果写回 `results/`，状态改成「已完成」。

跑通一次之后，这个仓库就是你和两个助手的共用工作台：任务有地方发，成果有地方查，进度有地方看。
